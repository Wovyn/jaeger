# muse-pi-yolo-mqtt

Intelligent object recognition and notification on the Raspberry Pi: the Pi Camera
captures frames at a low rate, YOLOv8 detects objects, results publish to MQTT only
when the detected scene changes, and a bounded ring buffer keeps event images
retrievable on demand. Node-RED consumes the MQTT events for notifications
(Pushover first) and other actions.

Wovyn R&D project. Apache 2.0.

## 1. Camera setup

The ArduCam IMX219 needs an explicit device-tree overlay. Unlike the official Pi
Camera, ArduCam modules don't carry the identification data that
`camera_auto_detect=1` looks for, so the firmware never detects them. Symptoms:

```
$ vcgencmd get_camera
supported=0 detected=0, libcamera interfaces=0
$ rpicam-hello --list-cameras
No cameras available!
```

> Gotcha (Oct 12, 2026): on this Pi (Debian 13) the live boot config is
> `/boot/firmware/config.txt`. `/boot/config.txt` is a 91-byte stub that says
> "DO NOT EDIT THIS FILE". Articles written for older Pi OS give the old path —
> edits there have no effect.

Steps (needs sudo):

```bash
sudo nano /boot/firmware/config.txt
# change:  camera_auto_detect=1  ->  camera_auto_detect=0
# under [all], add:  dtoverlay=imx219
sudo reboot
```

Verify:

```bash
rpicam-hello --list-cameras
# expect: 0 : imx219 [3280x2464 10-bit RGGB] ...

rpicam-still -t 1500 -o /tmp/cam-test.jpg && file /tmp/cam-test.jpg
# expect: JPEG image data ... 3280x2464 ...
rm /tmp/cam-test.jpg
```

If detection still fails: reseat the ribbon cable (blue-strip orientation matters;
the Pi 4 has a single CSI port) and confirm which camera model is attached —
non-IMX219 ArduCam modules need their own overlay or driver.

## 2. Python environment

```bash
python3 -m venv ~/projects/muse-pi-yolo-mqtt/venv
~/projects/muse-pi-yolo-mqtt/venv/bin/pip install --upgrade pip
```

### torch (CPU) — install FIRST, from the PyTorch CPU index

Default PyPI pulls the CUDA-bundled torch (~454 MB torch + ~651 MB cuDNN + more
NVIDIA packages, ~3 GB total, very slow) — useless on a Pi. Install the CPU build
first:

```bash
V=~/projects/muse-pi-yolo-mqtt/venv/bin
$V/pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
```

`torchvision` must come from the same CPU index: PyPI's torchvision against a
`+cpu` torch fails at ultralytics warmup with
`RuntimeError: operator torchvision::nms does not exist`.

### Everything else

```bash
V=~/projects/muse-pi-yolo-mqtt/venv/bin
$V/pip install ultralytics paho-mqtt
```

Verified working set (Oct 12, 2026): torch 2.14.1+cpu, torchvision 0.29.1+cpu,
ultralytics 8.4.176, paho-mqtt 2.1.0, opencv-python 5.0.0.93, numpy 2.5.4.

### picamera2

`pip install picamera2` does NOT work without sudo (its `python-prctl` dependency
needs libcap development headers). Install the distro package instead:

```bash
sudo apt update && sudo apt install -y python3-picamera2
```

Why it matters: capturing via the `rpicam-still` subprocess costs ~1–2 s per
frame in process startup; Picamera2 captures from a persistent camera object in
a fraction of a second. With YOLOv8n inference at ~4.6 s, the subprocess
overhead is the difference between hitting and missing the 5 s sample interval.

The venv must see the system package — recreate it with system site packages
and reinstall (pip's cache makes the reinstall fast):

```bash
rm -rf ~/projects/muse-pi-yolo-mqtt/venv
python3 -m venv --system-site-packages ~/projects/muse-pi-yolo-mqtt/venv
# repeat the torch / ultralytics / paho-mqtt installs above, then:
~/projects/muse-pi-yolo-mqtt/venv/bin/python -c "import picamera2; print('picamera2 ok')"
```

Status Oct 13: installed via apt, venv rewired with --system-site-packages,
verified — `import picamera2` ok, still capture 118 ms at 1280x720.
Fallback (if sudo is unavailable): frame capture via the `rpicam-still`
subprocess — proven working (see §4).

## 4. Verification (smoke test)

Proves the full chain: capture → inference.

```bash
V=~/projects/muse-pi-yolo-mqtt/venv/bin
rpicam-still -t 1500 -o /tmp/yolo-smoke.jpg
$V/python - <<'EOF'
from ultralytics import YOLO
import time
m = YOLO('/home/musecell/projects/muse-pi-yolo-mqtt/models/yolov8n.pt')
t = time.time()
r = m('/tmp/yolo-smoke.jpg', verbose=False)[0]
print('inference ms:', round((time.time() - t) * 1000))
for b in r.boxes:
    print(m.names[int(b.cls)], round(float(b.conf), 3))
EOF
rm /tmp/yolo-smoke.jpg
```

Measured Oct 12, 2026 (cold run, imgsz 640, Pi 4 CPU): yolov8n ≈ 4.6 s,
yolov8s ≈ 6.7 s per inference; a dark night frame correctly detected 0 boxes.
Warmed-up steady-state runs are faster. The 5 s default sample interval just
fits nano — see DESIGN.md §8 for the trade-offs (imgsz 416/320, longer interval
for the small model).

## 5. Configuration & running the service

### Generate config.json (on the Pi only)

Credentials live in `~/Documents/HiveMQ.txt` (never in git). Generate the
service config from it — secrets never leave the Pi:

```bash
cd ~/projects/muse-pi-yolo-mqtt
./venv/bin/python setup_config.py
# writes config.json with mode 0600
```

`config.json` layout: `mqtt` (host/port/username/password/tls/topic_root),
`cameras` (list; v0.1 has one `camera0` entry — id, name, type, resolution,
sample_interval, model, imgsz, confidence_threshold, watchlist, publish
toggles, heartbeat_interval), `buffer` (dir, cap_bytes, max_files,
jpeg_quality). See `config.json.example` for the full schema.

### Run in the foreground (test)

```bash
cd ~/projects/muse-pi-yolo-mqtt && ./venv/bin/python yolo_sensor.py
```

The service opens the camera, loads the model, connects to HiveMQ Cloud over
TLS, publishes its retained state (Pi config/status, per-camera config/status,
`{count: 0}` baselines for every watchlist class), then loops:
capture → inference → publish on per-class change → sleep.

### Run as a service (systemd)

```bash
sudo cp yolo-mqtt.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now yolo-mqtt.service
systemctl status yolo-mqtt.service
```

The unit runs as `musecell` (no sudo at runtime), restarts on failure.

### Remote configuration (MQTT)

Publish JSON to `.../camera0/config/set` — e.g. via Node-RED or mosquitto_pub:

| Key | Effect |
|---|---|
| `sample_interval` | seconds between captures (float) |
| `confidence_threshold` | 0–1 (float) |
| `watchlist` | list of COCO class names |
| `model` | `n`/`s` (or `yolov8n`/`yolov8s`) — reloads the model live |
| `buffer_cap_mb` | ring-buffer cap in MB |
| `heartbeat_interval` | seconds between config republishes |
| `publish` | `{"classId": bool, "className": bool, "events": bool}` |
| `capture_now` | `true` triggers an immediate capture cycle |

Changes persist back to `config.json` (mode 0600 preserved) and the camera's
retained `config` topic is republished. Example:

```bash
mosquitto_pub -h <broker> -p 8883 --capath /etc/ssl/certs \
  -u <user> -P <pass> \
  -t 'Wovyn/RaspberryPi/YOLOSensor/<serial>/camera0/config/set' \
  -m '{"sample_interval": 10}' -q 1
```

## 6. MQTT topic reference

Root: `Wovyn/RaspberryPi/YOLOSensor/<cpu-serial>/` (this Pi: `10000000968c1b38`).
All payloads JSON, timestamps ISO-8601 UTC, QoS 1.

```
<serial>/
├── config                  (retained) service identity: version, cameras
├── status                  (retained, LWT) online/offline
└── camera0/
    ├── config              (retained) camera details + tunables
    ├── config/set          incoming commands (see §5)
    ├── status              (retained) camera online/degraded/offline
    ├── events              scene-change summary {timestamp, counts, image_ref}
    ├── classId/0 …         (retained) per-class {count, detections, image_ref}
    ├── className/person …  (retained) same, by name
    └── images/
        ├── request         {event_id} → ask for an image
        └── response        {event_id, timestamp, jpeg_base64, detections}
```

Detection detail: `{confidence, bbox}` with bbox normalized 0–1 `[x1,y1,x2,y2]`.
A class publishes only when its count changes (including → 0, which clears the
retained state). The ring buffer (`buffer/camera0/`) stores the frame for every
published change; `image_ref` is the buffer event id.

## 7. Node-RED

Selective consumers sharing the one camera + inference:

- Person/occupancy: `Wovyn/RaspberryPi/YOLOSensor/+/camera0/className/person`
- Vehicles: `.../camera0/className/car` (or by id: `.../camera0/classId/2`)
- Simple notifier → Pushover: `.../camera0/events` (counts, no per-class state)
- Image on demand: publish `{event_id}` to `.../camera0/images/request`,
  read the JPEG from `.../camera0/images/response`.

## 9. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `No cameras available!`, `detected=0` | ArduCam needs `dtoverlay=imx219` + `camera_auto_detect=0` in `/boot/firmware/config.txt` (not `/boot/config.txt`), then reboot |
| `torchvision::nms does not exist` | torchvision must be the `+cpu` build from the PyTorch CPU index, matching the `+cpu` torch |
| pip tries to download ~3 GB of torch | default PyPI torch is CUDA-bundled; install torch+torchvision from `https://download.pytorch.org/whl/cpu` first |
| `pip install picamera2` build failure | needs `libcap-dev` (sudo) — use `sudo apt install python3-picamera2` instead |
| `import picamera2` fails in venv | venv needs `--system-site-packages` to see the apt package |
| service exits: `missing config.json` | run `setup_config.py` first |
| `AttributeError: 'NoneType' ... publish` (old) | fixed Oct 13: startup baselines now publish from `on_connect` |
